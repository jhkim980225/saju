## 맥락

2026-11-25 멱등성 점검은 같은 요청이나 알림이 두 번 들어오는 경우(재전송, 두 번 누름, 두 탭, 응답 유실 뒤 재시도)를 코드에서 찾았다. 그로블 문서를 확인한 결과 같은 ref 의 두 번째 결제를 막는 장치(멱등 키, 일회용 링크, 1인 1회 제한, 결제·환불 API)가 없었다. 결제 확인을 기다리다 구매 버튼을 다시 누르면 새 주문으로 한 번 더 결제되었고, 같은 결제창으로 두 번 결제하면 두 번째 결제는 기록 없이 무시되었다. AI 상담과 꿈풀이는 같은 요청을 두 번 보내면 질문권이 두 번 차감되었다. 운영자는 환불해야 할 결제를 로그를 봐야만 알 수 있었다.

## 결정

- 질문권을 쓰는 요청(AI 상담, 꿈풀이)은 클라이언트가 보낸 `requestId` 로 선점한다(`apps/api/src/lib/requestClaim.ts`). `webhook_events` 에 `<종류>:<사용자 ID>:<요청 ID>` 키를 먼저 넣은 요청만 처리하고, 같은 요청이 다시 오면 처음 답을 돌려준다. 처리 중이면 409 이고, 처리에 실패하면 선점을 풀어 다시 보낼 수 있다.
- 결제창으로 보내기 전에 막는다. 같은 상품·대상의 미결 주문이 30분 안에 있으면 409 `PAYMENT_IN_PROGRESS` 로 결제 확인 화면에 보내고, 다시 결제할 때는 같은 주문과 같은 ref 를 쓴다. 이미 가진 리포트를 다시 주문하면 409 `ALREADY_OWNED` 다.
- 그래도 생긴 중복 결제는 질문권 팩이면 새 주문으로 지급하고, 그 밖의 상품이면 지급하지 않고 `DUPLICATE_PAYMENT` 로 기록한 뒤 환불 필요 알림을 보낸다.
- refresh token 을 회전할 때 이어 받은 토큰(`replaced_by`)을 적고, 30초 안의 재사용이며 이어 받은 토큰이 살아 있으면 새 토큰을 준다.
- 운영 알림을 `OPS_ALERT_WEBHOOK_URL` 의 Discord 채널 웹훅으로 보낸다(`apps/api/src/modules/ops/service.ts`). 가입, 결제 완료, 환불, 환불 필요, 결제 확인 지연(30분), 웹훅 서명 실패, AI 장애, 서버 오류는 바로 알리고, 매일 08:00 KST 에 어제 요약을 보낸다.
- 알림에는 이메일, 이름, 생년월일, 질문 내용을 넣지 않고 가입 방식, 상품, 금액, 주문 번호만 적는다.

## 근거

- 그로블에서는 같은 ref 의 중복 결제를 막을 수 없으므로 우리 쪽에서 결제 전에 막아야 했다(PAYMENTS.md §2.1).
- 수정 전 코드에서 새 멱등성 테스트 4건이 실패했다(SECURITY_REVIEW.md).
- 알림은 응답 뒤(`waitUntil`)에 보내 사용자 응답을 늦추지 않는다.

## 결과와 영향

얻은 것:
- 두 번 누름과 재전송으로 생기는 중복 차감과 중복 결제가 줄었고, 운영자는 환불할 결제를 알림으로 바로 안다.
- 결제 웹훅 검증 실패와 AI 잔액 부족 같은 장애를 로그를 보지 않고 안다.

감수한 것:
- 결제를 마친 뒤 브라우저 뒤로 가기로 그로블 결제창에 돌아가 다시 결제하는 것은 여전히 막을 수 없다. 질문권 팩이 아닌 상품은 운영자가 직접 환불한다.
- 웹훅 기록용 `webhook_events` 테이블이 요청 선점 기록도 함께 담는다.
- 10분마다 도는 Cron 작업과 집계 테이블 `ops_counters`(40일 보관), `users.registered_at` 컬럼이 늘었다(마이그레이션 0003·0004).
- 30초 유예 때문에 refresh token 재사용 탐지의 범위가 좁아졌다. 로그아웃이나 비밀번호 변경으로 끊긴 세션은 이어 받은 토큰도 폐기되어 있어 유예하지 않는다.
- 하루 요약의 AI 비용은 코드 안 단가표와 환율 1,450원으로 어림한 값이다.
