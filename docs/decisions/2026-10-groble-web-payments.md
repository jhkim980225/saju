  - `738028f` 한 그로블 계정을 여러 서비스가 쓰도록 ref 접두어(`GROBLE_REF_PREFIX`) 추가

## 맥락

첫 커밋의 웹 결제는 토스페이먼츠 결제창(1순위)과 포트원 V2(2순위)를 쓰고, 서버가 결제사 승인 API 로 금액을 다시 확인하는 구조였다. PAYMENTS.md §3.0 에 따르면 PG 심사에는 사업자등록, 통신판매업 신고, 사업자 정보 표기가 먼저 필요하다. 토스페이먼츠는 가입비 220,000원과 연관리비 110,000원이 들고, KG이니시스·키움페이·엑심베이·네이버페이는 사주·운세 업종이 입점할 수 없다.

## 결정

- 웹 결제는 그로블 결제창으로 한다(`PAYMENT_PROVIDER=groble`). 사용자 결정이다.
- 그로블은 결제창마다 가격이 고정이므로 상품마다 결제창을 하나씩 만들고 `GROBLE_PRODUCT_LINKS` 에 연결한다.
- 그로블에는 승인·취소·조회 API 가 없으므로 결제 확정과 환불 회수는 HMAC 서명된 웹훅으로만 한다. 웹훅의 ref, 결제창 ID, 금액을 주문과 대조한 뒤 지급한다.
- 한 그로블 계정을 다른 서비스와 같이 쓰므로 ref 를 `<접두어>-<주문 ID>` 로 보내고, 다른 접두어의 알림은 기록만 하고 건너뛴다. 운영 접두어는 `saju` 다.
- 토스페이먼츠·포트원 연동 코드는 지우지 않고 대안으로 남긴다. 앱은 스토어 인앱결제를 그대로 쓴다.

## 근거

- PRD §3 과 §5 는 그로블을 고른 이유를 "사업자 등록 없이 판매"로 적는다. PG 의 선행 조건인 사업자등록과 통신판매업 신고 없이 판매를 시작할 수 있다.

## 결과와 영향

얻은 것:
- PG 심사와 계약 없이 2026-11-25 에 결제창 15개를 연결해 웹 결제를 운영하기 시작했다.
감수한 것:
- 서버가 결제를 직접 승인하거나 취소할 수 없다. 금액·결제창 불일치, 구매 한도 초과, 중복 결제는 지급하지 않고 운영자가 그로블 판매자 화면에서 환불한다. 관리자 환불 API 는 그로블 주문에 안내만 한다.
- 우리 가격과 그로블 결제창 가격을 사람이 맞춰야 한다. 쿠폰이나 할인을 켜거나 프로모션 종료일에 결제창 가격을 바꾸지 않으면 금액 불일치로 지급하지 않는다.
- 그로블은 알림 순서를 보장하지 않고, 같은 ref 로 두 번 결제하는 것도 막지 않는다. 이 때문에 환불 선행 처리와 결제 전 중복 차단을 따로 만들었다([2026-11-idempotency-ops-alerts.md](./2026-11-idempotency-ops-alerts.md)).
- 웹훅 주소는 스토어당 하나라 같은 계정을 쓰는 다른 서비스가 알림을 받아 이 서비스로 넘겨준다. 두 서비스가 같은 웹훅 시크릿을 쓰므로, 시크릿을 재발급하면 두 Worker 에 모두 넣어야 한다. 이 서비스의 결제 확정이 다른 서비스의 전달 코드에 달려 있다.
- 수수료 기록이 문서마다 다르다. PRD §3 은 총 약 8.7%, COSTS.md 와 PAYMENTS.md §3.5 는 외부 가이드 기준 4.4%(VAT 별도)로 적는다.
